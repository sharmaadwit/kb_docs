FRAMEWORK HIGHLIGHTS
====================

ANSWER ANATOMY (5 Required Sections)
────────────────────────────────────
1. Diagnosis (1-3 sentences)
   Signal: "Based on your question, I'm seeing..."
   Purpose: Show you understand their situation

2. Strategic Context (2-4 sentences)
   Signal: "Why this matters:"
   Purpose: Explain business impact, not just technical

3. Multiple Approaches (2-3 paths with trade-offs)
   Signal: "Approach 1 (Name) ... Approach 2 (Name) ..."
   Purpose: Surface viable options, not one right way

4. Recommended Path (2-4 sentences)
   Signal: "I'd typically start with..."
   Purpose: Suggest starting point (not prescriptive)

5. Open Questions (3-5 grouped questions)
   Signal: "To refine this recommendation, helps to know:"
   Purpose: Invite dialogue, highlight unknowns

TONAL SHIFTS
────────────
Old (Prescriptive)        → New (Advisory)
"Here's how to..."        → "Let me first understand..."
One right way             → Multiple paths with trade-offs
Risk not mentioned        → Explicit trade-offs for each path
"You must"                → "I'd typically..."
"I don't know"            → "I'm less certain about X"
Answer ends               → Dialogue invite: "Does this match your situation?"

CONDITIONAL LOGIC PATTERNS
──────────────────────────
Use "If X → Path A; If Y → Path B" when:
✓ Each path has materially different outcomes (cost, complexity, time)
✓ You can detect which condition applies
✓ The choice is reversible
✓ There's a default/recommended path

Don't use when:
✗ All paths are equally valid (just list them)
✗ Conditions are too vague ("if you care about quality")
✗ You're guessing (ask first instead)

ACCURACY MAINTENANCE
────────────────────
1. Confidence tagging: HIGH/MEDIUM/LOW based on KB evidence count
2. Source transparency: "Documented in 10+ case studies" vs. "One customer reported"
3. Preconditions: "Works best for [profile]" vs. universal claim
4. Uncertainty admission: "Less certain here; I'd test first"
5. Conditional language: "One approach is..." vs. "You must..."
6. Data anchoring: Cite metrics ("92% open rates") not vague ("high")

KEY INSIGHTS
============

1. Consulting tone = Strategy, not Just Tactics
   Old: "Here's step 1, step 2, step 3"
   New: "Here's why this matters, here's how others approach it, here's what I'd try first"
   Impact: Users make better decisions, fewer wrong implementations

2. Multiple Paths > Single Answer
   When customers see 2-3 viable approaches with trade-offs, they:
   - Choose confidently (informed decision)
   - Adapt faster (know why they chose path A, can switch to B if needed)
   - Build trust (you're not hiding alternatives)

3. Accuracy Through Uncertainty
   Confidence tagging doesn't hurt accuracy; it helps:
   - "90% confident from 15 case studies" builds more trust than "You must"
   - Admitting unknowns ("less certain about X") shows honesty
   - Users respect nuance and self-awareness

4. Dialogue > One-Way Delivery
   Questions at the end aren't filling empty space; they:
   - Invite refinement (customer clarifies their actual need)
   - Build relationship (assistant asking back = partnership)
   - Reduce wrong implementations (ask first, then decide)

5. Consulting Answers Are Longer, But Scannable
   Yes, 2-3x word count. But:
   - Headers let users skim
   - Bullets are skimmable
   - TL;DR option: 2-sentence summary + "want details?"

6. Phased Rollout Reduces Risk
   Don't flip switch to all answers at once:
   - Start with compare intent (naturally high-value, high-complexity)
   - Measure engagement & accuracy
   - Expand only if results are positive

7. This Matches Existing Patterns
   Your KB already has:
   - RCS consulting-tone questions (RCS_CONSULTING_QUESTIONS_TEST.md)
   - Case studies with real metrics (already built)
   - Compare intents with multiple entities (already routing)
   - This framework just formalizes what works

COMMON QUESTIONS
================

Q: Will this make answers worse?
A: No. Consulting answers start with diagnosis (shows understanding), so users
   see you "get it" before diving into solutions. This builds trust first.

Q: What if consulting answers are too long?
A: They are longer. Offer summary + details: "Here's the 30-second version.
   Want to explore it?" Users can choose depth.

Q: How do we ensure accuracy?
A: Confidence tagging, evidence counts, uncertainty admission. Users prefer
   "I'm 80% confident, test it" over silence.

Q: What if user doesn't answer the open questions?
A: That's OK. Questions are invitations, not requirements. Users can implement
   the recommended path immediately if they want.

Q: Isn't this overkill for simple queries?
A: For definitions, yes—keep those brief. For setup/compare/troubleshooting,
   consulting tone saves users from wrong implementations. High ROI on that.

Q: How long does this add to answer time?
A: ~200-500ms composition time. Answer delivery stays fast. Users see slight
   delay from 2s to 2.5s—imperceptible if content is valuable.

Q: Should every answer be this format?
A: No. Use consulting tone for high-stakes decisions (setup, compare, 
   troubleshooting). Keep simple definitions brief.
